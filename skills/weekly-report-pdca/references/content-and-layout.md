# 周报内容与布局规范

## 1. 事实优先

把原始记录先拆成事实字段：周期、项目、目标、动作、结果、证据、状态、问题、依赖、负责人和日期。缺少的字段保持“待确认”，不要从语气或上下文推断数字、进度或客户态度。

推荐句式：

> 动作 + 对象 + 结果 + 证据/时间

例如：“完成延锋软件 12 项功能开发，客户演示通过，8/17 - 8/20 进入现场部署。”

避免：“持续跟进项目”“完成相关测试”“参加客户会议”。这些只能说明活动，不能说明结果。

## 2. PDCA 写法

| 环节 | 必须回答的问题 | 常见证据 |
| --- | --- | --- |
| Plan | 本周要达成什么？完成标准是什么？ | 目标、范围、节点、交付物 |
| Do | 实际做了什么？采用了什么方案？ | 开发、测试、评审、部署、沟通 |
| Check | 结果是否达到标准？偏差在哪里？ | 测试结果、客户反馈、完成数量、故障根因 |
| Act | 下周改变什么？谁在何时完成什么？ | 修正动作、决策、待验证项、协调请求 |

每个重点项目至少要有一条 Check 和一条 Act。尚未验证时写“验证中”，不要把 Do 当成 Check。

## 3. 模块化页面层级

页眉是唯一固定模块：标题、周期、汇报人和范围。其余模块按事实选择，不要求每周完整出现：

1. 本周摘要：有清晰结论或指标时使用，通常 1-5 条。
2. 重点工作流：可重复任意次；每项可以是项目、专项、现场工作、问题处置、跨团队协作或会议决策。
3. 可选专题：工具、流程、知识沉淀、客户沟通、调研、组织协作等，标题应与真实内容一致。
4. 下周计划：只有确认的行动项时使用。
5. 风险与协调：只有实际风险、依赖或升级请求时使用。

不要为“个人事项”“工具改进”“项目 A/B”等固定标题预留空白。摘要必须先于细节；计划和风险使用全宽区域；工作流详情可在桌面端使用单列或多列，在窄屏端自动单列。

## 4. 计划与风险

下周任务必须可验收。把“参与项目”扩展成“参与项目，完成技术路线确认并输出路线结论/待确认清单”。

风险至少包含：

- 风险事实：现在发生了什么；
- 影响：可能影响哪个节点、交付物或质量指标；
- 应对：下一步做什么；
- 协调：需要谁在什么时候提供什么支持。

## 5. 视觉约束

- 使用一个主色、一个成功色和一个风险色，颜色承担状态含义。
- 通过标题、留白、边框和表格分组，而不是堆叠装饰性卡片。
- 首屏展示本周结论，正文控制段落长度；数字、日期、P0/P1/P2 要容易扫描。
- HTML 只使用本地 CSS 和系统字体，保证离线打开、打印和窄屏阅读。
