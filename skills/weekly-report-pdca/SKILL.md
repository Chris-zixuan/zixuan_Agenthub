# 周报 PDCA

## Overview

将零散工作记录整理成可快速阅读、可追踪和可复盘的周报。默认面向软件、自动化、项目交付和研发团队，输出中文内容；需要网页交付时使用 `assets/weekly-report-template.html`，需要详细写作判断时读取 `references/content-and-layout.md`，需要数据聚合细节时读取 `references/obsidian-data-source.md`。

## Workflow

0. **确定周范围**：计算当前 ISO 周编号（周一至周日），生成本周 7 天日期列表；目标 Markdown 文件 `1_日志/YYYY/YYYY-Www.md`，HTML 文件同目录 `1_日志/YYYY/YYYY-Www.html`。周报已存在时询问覆盖还是跳过；跨月周放在日志数量更多的年份目录。
1. **收集数据**：遍历本周 7 篇日志 `1_日志/YYYY/YYYY-MM-DD.md`（缺失的天跳过），按 `references/obsidian-data-source.md` 的分段规则提取工作记录、英语打卡、健身、生活、所思所想与 wikilinks。用户直接提供材料时以用户材料为准。不要把推测写成事实；缺少数据时使用"待确认"或提出最少的澄清问题。
2. **归类内容**：先识别本周实际存在的工作流、专项、会议结论、交付物和异常事项，再选择合适模块。摘要、计划、风险和沉淀均可省略；不要为了套模板新增空章节，或把不同事项强行归入"项目"。
3. **应用 PDCA**：对适合闭环呈现的重点工作流写 Plan、Do、Check、Act。一个工作流可以是项目、专项、现场问题或跨团队协作，不限制数量。Plan 写目标和完成标准，Do 写实际动作，Check 写测试/客户/数据等验证结果，Act 写偏差修正和下一步。若某环节没有事实，明确标记缺口，不补造结论。
4. **写成结果**：优先使用"动作 + 对象 + 结果 + 证据"的句式。把"参加会议、持续跟进、进行测试"改写为可验证的交付或状态；保留关键日期、数量、负责人和依赖。
5. **编排输出**：先给管理者一页摘要，再给重点工作流细节。只有有可执行事项时才添加下周计划；有计划时必须包含优先级、时间、负责人（已知时）、交付物/完成标准和依赖。只有有真实风险或协调请求时才添加风险模块，并写影响与协调动作。
6. **输出 Markdown 待审批**：按 `references/obsidian-data-source.md` 的周报 Frontmatter 规范写入 `1_日志/YYYY/YYYY-Www.md`，正文含本周摘要（含关键数字）、项目进展、学习进度、生活摘要、所思所想精选、下周计划、本周日志。写入后**停在此处，向用户展示 Markdown 内容并等待审批**，不进入下一步。
7. **用户审批与修改**：用户审阅 Markdown，可提出修改意见。根据用户反馈调整内容（事实、结构、语气、措辞），更新 `1_日志/YYYY/YYYY-Www.md`，直到用户明确同意。未获同意前不得生成 HTML。
8. **生成 HTML（用户同意后）**：仅在用户明确同意 Markdown 内容后，复制 `assets/weekly-report-template.html`，基于已定稿的 Markdown 填入数据（保持内容一致），输出到 `1_日志/YYYY/YYYY-Www.html`。工作流模块可重复任意次；不要保留空模块、固定数量的指标或虚构的项目栏位。用户只要文字时输出 Markdown 或纯文本，不生成多余文件。
9. **验证**：检查所有原始事实是否保留、计划是否可执行、风险是否有动作、PDCA 是否闭环、HTML 是否有成对的结构标签且桌面/窄屏不出现横向溢出。修改已有文件前先读取并尊重其现有内容，避免无关改写。

## Content Modules

- **基本信息**：始终保留周期、汇报人和范围；总体状态仅在有明确判断时显示。
- **本周结论**：有 1-5 条值得先读的结果时使用，包含数量、日期、客户反馈或测试状态等证据。
- **重点工作流**：可重复任意次。每项可代表项目、专项、现场交付、故障处置或跨团队协作；按事实选择 PDCA 的完整或部分字段。
- **专题与沉淀**：按需放入工具、流程、知识、会议结论或其他不属于重点工作流的事项；标题应随内容重命名。
- **下周计划**：仅在存在已确认行动时使用；按 P0/P1/P2 排序，包含事项、时间、负责人、交付物/完成标准和依赖。
- **风险与协调**：仅在存在需要升级或跟进的事项时使用，包含风险、影响、应对动作、协调对象和截止时间。

## Writing Constraints

- 用结果、状态和证据表达，不以活动清单替代进展。
- 一项任务尽量只表达一个主要结果；长段落拆成短句、列表或表格。
- 区分"已完成、进行中、阻塞、待确认"，不要用模糊的"基本完成"。
- 事实不足时保留不确定性；不得擅自补全时间、百分比、负责人或客户态度。
- 计划不是愿望清单：每项必须能判断"下周结束时是否完成"。
- 颜色只用于状态和优先级；HTML 模板保持简洁、可打印、响应式，不引入外部依赖。
- HTML 中的"模块可选""可重复"注释是生成指令，不应在最终报告中保留占位内容或空白区块。
- 日志缺失的天跳过，并在输出中说明覆盖范围，不臆造当天内容。

## Resource Routing

- 需要完整内容规则、句式和布局取舍时，读取 `references/content-and-layout.md`。
- 需要从 Obsidian 聚合本周日志、周报 Frontmatter 规范与存储位置时，读取 `references/obsidian-data-source.md`。
- 生成新的网页周报或需要统一视觉时，复制 `assets/weekly-report-template.html`，再替换示例内容和数据属性；先删除不适用模块，再按需要重复 `.workstream`、`.summary-item`、计划行或风险项。
- 修改已有 HTML 时，优先保留原有事实和可识别的章节；不要为了套模板而删除用户内容。
