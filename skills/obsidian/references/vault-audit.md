# 分析层 · Obsidian 知识库整体分析

用于对**整个** Obsidian 库做一次性体检并产出结构化报告（而不是整理某一篇笔记）。

**本层只读。** 发现的脏文件、空目录、失效链接只写进建议，**不要顺手改** —— 等用户确认。

> 命令用法见 `cli-reference.md`。库规范以 `9_系统/协作约定.md` 为准。

## 何时用

- 用户要求分析整个知识库 / 知识库体检 / 找重复与陈旧内容 / 输出分析报告
- 不适用：单篇笔记整理（走运维层 `kb-maintenance.md` 或常规整理流程）

> 触发词辨析：「知识库体检」指本层（重，出 HTML 报告）；「健康看板扫描」属运维层（轻，纯文本）。

## 四步流程

### Step 1 · 侦察（不要跳过）

```bash
cd {vault} && for d in */; do printf "%-16s md=%s total=%s\n" "$d" "$(find "$d" -name '*.md' | wc -l | tr -d ' ')" "$(find "$d" -type f | wc -l | tr -d ' ')"; done
find {vault} -maxdepth 1 -name '*.md'
```

同时抓：二级目录树（`find . -maxdepth 2 -type d`）、空目录（`find . -type d -empty`）、重名文件。

**必须确认**：库内约定文件（如 `AGENTS.md` 承诺的导航文件）是否真实存在。承诺存在但实际缺失的文件，是报告里价值最高的发现之一。

### Step 2 · 拆子集 → 分派并行子代理

按**顶层板块**拆，单个子集控制在 30–200 篇：

- 大板块按目录再切（如日记按年份切成 2 个子集）
- 系统 / 收件箱 / 根目录杂项合成 1 个"碎片子集"
- 子集数 6–8 个为宜

**所有子代理必须在一条消息里并行发出**（多个 Agent 工具调用同一次响应）。每个子代理的 prompt 必须自包含，包含：

1. 库背景 + 根目录绝对路径 + 全库总量
2. **严格只读约束**（禁止 Write/Edit，只用 Read/Grep/Glob 与只读 Bash）—— 不写这条，子代理会动手改文件
3. 精确的路径范围与已知目录结构
4. 该子集的**专项检查项**（如"逐文件对照两套编号体系是否重复""统计提及项目却无 wikilink 的篇数"）
5. 统一输出模板：①内容清单与结构 ②主题与领域分布 ③覆盖与空白 ④重复与陈旧 ⑤质量评估（1–5 分+理由）⑥改进建议
6. 字数上限（900–1000 字）；抽样策略（重点读导航 / 首页 / 体量最大 / <300B 空壳，不要逐字读完）
7. 敏感目录（私人笔记、密码文件）**只报告存在与结构，不读取内容**

### Step 3 · 主代理跑全库量化扫描

子代理给质性判断，量化扫描给数字口径，两者交叉验证。

**优先用官方 Obsidian CLI 取基础数字**（前提：Obsidian 正在运行且已开启 CLI；命令见 `cli-reference.md`）。比手写脚本更快，且是 Obsidian 自己的索引口径：

```bash
obsidian vault            # 库信息：文件数/目录数/体积
obsidian unresolved       # 全库断链（一条命令替代整份断链扫描脚本）
obsidian orphans          # 无入链页
obsidian deadends         # 无出链页
obsidian tags             # 全库标签（含层级，如 #标定/手眼标定）
obsidian properties       # 全库属性名及使用情况
obsidian unresolved | wc -l   # 断链计数
```

> 体检时只用只读命令（`unresolved`/`orphans`/`deadends`/`tags`/`vault`），**切勿裸调写入类命令试探** —— 部分命令无参数会直接执行。

⚠️ 口径提醒：`obsidian unresolved` 会把 Clippings 等笔记里的**相对路径图片 / 外链**（`./assets/x.png`、`../../commit/xxx`）也算作未解析，计数前要按目录过滤，否则会显著高估。

CLI 拿不到的部分仍用 Python 脚本补：frontmatter 覆盖率、tags 写法四态、双链解析率、**按目录分组**的孤立页、<200B 空壳文件。

跑一份 Python 脚本统计：

- 各目录 md 数 + frontmatter 覆盖率 + 无 frontmatter 清单
- frontmatter 字段覆盖（`defaultdict(Counter)`）
- `tags` 写法**必须分四态解析**：`tags: []` / 裸 `tags:` / 行内数组 / **块状多行列表**。
  ⚠️ **这是本层最容易出错的一步，曾因此产出一份数字全错的报告**：有相当比例的笔记（某库 770 篇中占 277 篇）用 `tags:` 换行 + `- 标签名` 的写法，**值在下一行**。任何只读 `tags:` 行内容的正则都会把它们误判为空值，导致「空值率」被严重高估（某库实测 50% 有值被误报为 5%）。
  正确做法：读到 `tags:` 后若该行值为空，**继续向下读取缩进的 `- ` 列表项**，直到遇到非列表行；或用 `yaml.safe_load` 整块解析 frontmatter。**上报任何「XX% 为空」的结论前，先抽一篇块状写法的笔记人工验证脚本判定是否正确。**
- 双链：引用总次数、唯一目标、可解析/不可解析（目标名取路径末段，比对全库文件名集合）
- 孤立页：零入链笔记数，并**按目录分组**（日记是天然叶子，要单独剔除后另算）
- <200B 空壳文件、重复日期 / 重名文件

> **数字复核纪律**：子代理与主脚本给出的**每一个计数**都要在写进报告前用第二种方法复算一次。同一指标换段代码就会漂（实测偏差案例：别名链接 443→419、行尾双空格 61→40、assets 文件 113→103）。质性判断可以信子代理，**计数必须回主代理复核**。

**排除目录**：`.obsidian`、`.trash`、`.workbuddy`、`.agents`、`.git`。

### Step 4 · 汇总报告

产出两份，放在 `9_系统/`：

- `知识库整体分析报告-YYYY-MM-DD.md`（库内长期留存、可 wikilink）
- 同名 `.html`（可读版，用户拿去看）

报告骨架：

1. **执行摘要** —— 一句话结论 + 按严重度排序的核心发现表（每条带证据数字）
2. **统计概览** —— 板块规模 / frontmatter 覆盖率表、双链健康度、悬空链接 TOP10、元数据现状
3. **分板块诊断** —— 每板块一张卡：定位 / 构成 / 强项 / 主要问题 / 评分
4. **五维横向结论** —— 结构组织、主题分布、覆盖空白、重复陈旧、整体质量（用 A/B/C 分层）
5. **改进建议** —— P0（本周，落到具体文件名与链接名）/ P1（本月，结构性）/ P2（长期机制）
6. **附录** —— 分工表、关键文件、测量口径

最后用 `present_files` 呈现（HTML 放首位优先预览），并在正文给一段核心发现摘要。

## 踩过的坑

- **mtime 不可信**：全库文件时间可能被同步 / 复制重置成同一天。陈旧度只能用文件名日期 + frontmatter 内容判断，并在报告口径里明确写出来。
- **悬空链接 ≠ 断链**：`[[概念名]]` 可能是有意指向未来笔记。报告里要区分"指向概念"和"真断链"，或用措辞"未解析 / 悬空"。
- **子代理会得出冲突结论**（如"某文件有两份副本"vs"只有一份"）。**必须主代理亲自 `find` 复核**再写进报告。
- **孤立页要剔除日记**，否则数字会被叶子节点淹没。
- 涉及私人内容（家庭、感情、健康、密码）的子代理要显式约束：只做结构与质量分析，不转述细节。
- 发现的脏文件 / 空目录 / 失效链接**只写进建议，不要顺手改** —— 等用户确认。
- **能用 CLI 就不要手写扫描脚本**：`unresolved` / `orphans` / `deadends` / `tags` 都是 Obsidian 自己的口径，比正则匹配更准（尤其能正确解析别名与相对路径）。
